# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

vitterm is a native macOS terminal (Swift 6 toolchain in Swift 5 language mode, Metal, AppKit, macOS 14+). The emulation core is written from scratch; there are no third-party dependencies.

## Commands

```sh
swift build                              # debug build
swift run vitterm                        # run without bundling (shaders compile at launch)
./scripts/bundle.sh                      # release build/vitterm.app (offline metallib, resources, ad-hoc signed)
open build/vitterm.app

scripts/test.sh                          # all unit/integration tests, then vitbench --check (release)
scripts/test.sh --quick                  # tests only, skip the perf gate
scripts/test.sh --e2e                    # also builds build/e2e/vitterm.app (with test hooks; bundle id dev.vitterm.vitterm.e2e, so it never stands in for the real app) and drives it (opens windows)
scripts/test.sh --extended               # InvariantTests/DifferentialTests at 20x (VITTERM_FUZZ_SCALE=20)

swift test --filter VitCoreTests.EmulationTests            # one test class
swift test --filter "VitCoreTests.ParserTests/testFoo"     # one test
VITTERM_E2E=1 swift test --filter E2ETests                 # needs TEST_HOOKS=1 APP=build/e2e/vitterm.app ./scripts/bundle.sh first

swift run -c release vitbench [all|parse|pty|render|reflow|search] [--mb N] [--check]
```

Performance numbers only mean anything in release builds (`VitCore` is compiled with `-Ounchecked` in release).

**Security rule:** everything a program writes to the terminal is untrusted (including remote hosts over ssh). Because release builds of `VitCore` have no overflow checks, clamp every number parsed from escape sequences before doing arithmetic with it (`ImageStore.clampCells`, CSI params are capped at 65535), bound every buffer or table that output can grow, and never let a reply echo program-supplied text. Add a case to `Tests/VitCoreTests/SecurityTests.swift` for any new input path. Run `vitbench --check` after touching hot paths: it exits non-zero when a budget regresses.

`Sources/VitCore/WidthTable.swift` is generated by `scripts/gen_width.py`; don't edit it by hand.

The app icon is built by `scripts/make_icon.swift` from `Resources/AppIcon-source.jpg` (it finds the dark rounded square, masks it and places it on the macOS icon grid); replace that image to change the icon.

## Architecture

Targets: `VitCore` (emulation, no UI), `VitPTY` (forkpty + read thread), `VitConfig` (config, themes, keybinds, file watcher), `VitRender` (Metal + CoreText; depends on Core and Config), `vitterm` (AppKit app), `vitbench` (benchmarks and perf gate).

**Data flow and threading.** Each pane is a `SurfaceView` (`Sources/vitterm/SurfaceView*.swift`) owning a `PTYProcess` and a `Terminal`. The PTY read thread calls `ptyOutput`, which takes `terminal.lock`, feeds bytes through `Parser` into `Terminal` (a `ParserHandler`), collects `pendingOutput` (replies to queries, written back to the PTY outside the lock) and wakes the main thread (`DispatchQueue.main.async`, coalesced) only while the display link is paused (`linkActive`); while it runs, each `tick` calls `drainOutput()` instead. Pausing goes through `stopLinkIfQuiet`, which decides under the lock so no output is missed. During sustained output the link is capped at 60 fps (`updateStreamingThrottle`). `TerminalRenderer.draw` skips a frame instead of calling `nextDrawable()` when 2 frames are still unpresented, so the main thread never blocks on the compositor. On the main thread, `wakeFromPTY` drains `terminal.pendingEvents` (title, bell, clipboard, cwd, etc.), and a `CADisplayLink` `tick` renders only when `terminal.dirty` or an animation is active, so an idle terminal draws nothing. Output that arrives while idle is drawn immediately (`renderNowIfIdle`) instead of waiting for the next tick. All `Terminal` state is shared across threads: any main-thread read or mutation must happen inside `terminal.lock.withLock { }`.

**Parser → Terminal.** `Parser` is a DEC/VT500 state machine with fast paths: SIMD scanning for printable ASCII (`printASCII`), bulk UTF-8 decoding (`printScalars`), and a tight CSI parameter loop. `Terminal` is split across `Terminal.swift`, `Terminal+CSI.swift` and `Terminal+OSC.swift`. Kitty graphics/iTerm2 images are in `Images.swift`.

**Grid.** `Line` (`Grid.swift`) is a class with manually managed `UnsafeMutablePointer<Cell>` storage. Only `cells[0..<used]` is meaningful; clearing just resets `used`. Scrollback lines are compacted to their content, and any write restores full capacity first. Lines are recycled, not freed. `uid` and `generation` (bumped on every content change) are the cache key that the renderer uses for shaping and atlas lookups, so content changes must bump `generation` or the screen will show stale content. `Line`'s own mutating methods bump it already. Code that writes through `cells` directly (as `Terminal`'s fast print paths do) must bump it itself. Reflow on resize rewraps logical lines using the `wrapped` flag.

**Rendering.** `TerminalRenderer.snapshot` copies only the visible, used cells under the lock. Shaping (`Shaper`, CoreText) and instance building happen after the lock is released. Shaped lines are cached by (uid, generation). CoreText runs are cached by content in a two-generation cache. Box drawing, block elements and Powerline glyphs are drawn procedurally (`BoxDrawing.swift`), not taken from the font. `renderImage` renders offscreen; render tests and `VITTERM_SNAPSHOT` use it.

**App layer.** `AppDelegate` owns the config and `ConfigWatcher` (kernel file events only, no polling: it watches the config file, each user theme file, and the nearest existing ancestor directories, and re-arms on every event), and calls `reloadConfig()` to push changes to every window. Each `TerminalWindowController` is a native macOS tab. A `TabController` holds a `SplitNode` tree (`SplitTree.swift`) of `SurfaceView`s. Keybinding actions are parsed in `VitConfig/Keybinds.swift` and dispatched in the app. Shell integration scripts (zsh, fish, bash) live in `Sources/vitterm/ShellIntegration` and are copied into the bundle.

## Testing conventions

- `InvariantTests` fuzz the terminal with random, deliberately split input and check structural invariants after every chunk. `Line.poisonReleasedCells` fills released memory with garbage so reads past `used` are caught. `VITTERM_FUZZ_TRACE=<file>` records the fuzzed input so a crash can be reproduced.
- `GrammarFuzzTests` generate random well-formed CSI/OSC/DCS/APC sequences with extreme parameters, Kitty graphics keys and iTerm2 image arguments. They run in debug builds, where overflow and out-of-bounds indexing trap, to find inputs that would corrupt memory in `-Ounchecked` release builds. Reproduce a crash with `VITTERM_FUZZ_TRACE=<file>` and run the test under `lldb` for the stack.
- `SecurityTests` hold one regression test per security fix, built from the attack input.
- `DifferentialTests` compare optimized paths against simple reference implementations: batched vs per-character printing (every cell), and the search index vs per-line regex. When you add a fast path, add a differential test against a naive version.
- `RenderTests` render offscreen with Metal and check pixels.
- E2E tests drive the bundled app through the debug env vars below.

## Debug environment variables

Only honored in debug builds and test-hook builds (`#if DEBUG || VITTERM_TEST_HOOKS`, see `DebugSnapshot.hooksEnabled`); the normal release bundle ignores them.

- `VITTERM_SNAPSHOT=/path.png`: render the focused tab offscreen after `VITTERM_SNAPSHOT_DELAY` seconds. Add `VITTERM_SNAPSHOT_QUIT=1` to exit afterwards.
- `VITTERM_DEBUG_ACTIONS='new_split:right;;text:ls\r'`: replay keybinding actions at startup.
- `VITTERM_DEBUG_DUMP=/path.json`: dump windows, tabs, panes (with their text) and config.
- `VITTERM_DEBUG_LATENCY=/path.txt`: log output-to-screen latency. `VITTERM_DEBUG_STARTUP=1`: print startup phase timings.
- `vitterm -e <command>` runs a command instead of the shell.

The user config is `~/.config/vitterm/config`. User themes go in `~/.config/vitterm/themes`.
